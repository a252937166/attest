What only an evidence-gated agent does

Four mechanisms, each recorded in the bundle. The figures show the recorded facts of real runs, not illustrations.

Tests before code

A test written after the patch can be shaped by the patch. Attest seals the acceptance tests from the contract first, proves they fail on the base, and only then lets the implementer start. At verification the same file, by digest, must pass.

A verifier that cannot be persuaded

The supervisor never imports the candidate's code. Each sealed test runs in its own child process under an unprivileged user with a timeout; the child cannot modify the tests or the verifier. Results are bound to the run's nonce, the file digests and two canaries, and any nonzero exit, signal, timeout or forged result refuses VERIFIED.

Break it before you trust it

Every changed line is mutated one way at a time; the sealed tests must notice. A second model writes tests against the patch. When a generated test fails, an arbiter classifies it; a correction counts only if it keeps every test, changes only the failing ones, passes on the candidate and still fails on the base or is caught by a mutant, and then the gate is re-run. A sealed test that failed by assertion or by an exception raised in the code under test is never overridden.

One recorded rule

The verdict is a pure function of the recorded gates. A skipped gate never counts as a pass, no model opinion enters, and the rule is written into every bundle so that the offline check re-derives the same verdict.

Architecture

The pipeline runs on the console host. Every model call goes to Nebius Token Factory; every execution happens in a Token Factory Sandbox branched from one retained checkpoint.

Separation of instances
The specifier, the sealer, the implementer, the breaker and the arbiter are separate model instances with separate contexts; none sees the others' private material.
Budget discipline
Every call is priced into the ledger under a per-run and a daily cap; an uncertain call is counted at its reservation and never replayed, because a replay could create a second billed sandbox or completion.
Provenance
Each bundle records the Attest revision, the supervisor digest, sampling settings and limits, so a reviewer knows exactly which code produced it.

Inside a Proof Bundle

Everything a reviewer needs ships in one directory, listed in a manifest written last. The offline checker re-derives digests, bindings, ledger totals and the verdict from the raw records.

How to use it

Everything on this console is public. No account is needed; a team token only reveals a private inference profile.

  1. 1

    Pick a sample task

    A small Python repository at a pinned state with a precise request, acceptance criteria and a write scope. Your own repository goes through the command line at a pinned commit.

  2. 2

    Browse, or run it live

    Browsing opens the latest recorded Proof Bundle at no cost. A live run spends up to a capped amount per run, a few runs per visitor per hour; recorded runs took a few minutes. You can leave the page; the run keeps its place.

  3. 3

    Read the verdict, then check it yourself

    The decision header cites the exhibit that matters. Download the bundle and re-derive everything offline:

    python -m attest check proof-bundle.zip
