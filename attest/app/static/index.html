Patches should arrive with proof.

Attest is a coding agent that has to prove its patch before you merge it. Acceptance tests are sealed before any code exists, the candidate is verified in a fresh sandbox by a supervisor that never imports its code, mutants and adversarial tests try to break it, and one recorded rule turns the evidence into a verdict.

Models propose, deterministic code disposes.

A plausible patch is not a verified one.

Coding agents write patches that look right, and their own review can be talked into agreeing. A reviewer needs something that cannot be persuaded: tests written before the code existed, executed by a process the candidate cannot influence, and a verdict derived from the record rather than from a model's confidence.

Tests before code
An independent Nemotron instance seals the acceptance tests from the contract. They must fail on the untouched repository before the implementer starts.
A verifier that cannot be persuaded
A supervisor that never imports the candidate's code runs each sealed test in its own unprivileged process, bound to a per-run nonce, the sealed file's digest and two canaries.
Attack the result
One-line mutants must be caught, a second model writes tests against the patch, a drift audit compares the action trail with the request, and an arbiter classifies every generated-test failure.
One recorded rule
The verdict follows from the gates alone and ships in a Proof Bundle with numbered exhibits, counterexamples, the usage ledger and a manifest you can re-check offline.

How a run earns its verdict

Five phases, each recorded in the bundle. The models write tests, patches and audits; deterministic code runs, binds and decides.

  1. 1Seal
  2. 2Implement
  3. 3Verify
  4. 4Break
  5. 5Attest

  1. Seal

    Nemotron 3 Ultra writes the specification; Nemotron 3 Super seals the tests

    Acceptance tests are written before any code exists and shown failing on the unmodified checkpoint: the red check.

    E1sealed tests

  2. Implement

    Nemotron 3 Super in a Nebius sandbox branch

    The implementer reads, edits and runs the existing tests through validated JSON actions inside the write scope the task names. It never sees the sealed tests.

    Patchdiff, digests, scope check

  3. Verify

    Attest's supervisor, deterministic code

    A fresh branch runs the sealed suite one process per test under an unprivileged user. Results are bound to the run's nonce, the sealed file's digest and verifier canaries. The existing and held-out suites run in their own branches.

    E1E4bound results

  4. Break

    Nemotron 3 Super writes adversarial tests; Nemotron 3 Ultra audits and arbitrates

    Mutants of the patch must be caught, adversarial tests run against it, a drift audit compares the trail with the request, and an arbiter classifies each failing generated test.

    E2E3E5E6breaker, audit, arbitration

  5. Attest

    One recorded rule, no model

    The verdict is derived from the recorded gates. The Proof Bundle carries the exhibits, the counterexample when there is one, the ledger and a manifest; an infrastructure failure is recorded as E7, never retried silently.

    E7failure record, when any

VERIFIED

Every gate passed in a fresh sandbox. Accept with the evidence.

NEEDS HUMAN

A gate failed or a generated test disagrees with the patch. Hold and decide.

INFEASIBLE

The specification stage found the request contradictory or impossible as written.

NO CHANGE

The implementer finished without changing any file.

ERROR

The run did not complete. Nothing was certified.

Who provides the core capabilities

Inference and execution are Nebius and NVIDIA services; the verification, binding and verdict logic is Attest's own code and runs on the console host.

How to use it

Everything on this console is public. No account is needed; a team token only reveals a private inference profile.

  1. 1

    Pick a sample task

    Each task is a small Python repository at a pinned state with a precise request, acceptance criteria and a write scope. The console serves the sample tasks; your own repository goes through the command line at a pinned commit.

  2. 2

    Browse the recorded evidence, or run it live

    Browsing opens the latest recorded Proof Bundle at no cost. A live run starts a new pipeline on Nemotron with a capped budget per run and a few runs per visitor per hour; recorded runs took a few minutes. You can leave the page: the run keeps its place and appears in the history with its verdict.

  3. 3

    Read the verdict, then check it yourself

    The decision header says whether you can accept the patch and cites the exhibit that matters. Download the Proof Bundle and re-derive every digest, binding and the verdict offline:

    python -m attest check proof-bundle.zip

    An integrity check of the record, not a signature: it proves the bundle is internally consistent and that the verdict follows the rule, not that the sandbox operations happened.
